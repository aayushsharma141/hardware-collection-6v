<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| URL path segment -> GROQ query | The `slug` param is genuinely visitor-controlled — anyone can request any path |
| Sanity content -> rendered JSX | Category and space editorial fields rendered into the page |
| Sanity settings -> WhatsApp href | Contextual CTA link construction |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-9-02 | Tampering | GROQ slug parameterization | mitigate | The slug is passed as a fetch parameter via `client.fetch(query, { ... })`, never interpolated into the GROQ template literal. This is the phase's primary injection surface because the slug is the one truly visitor-controlled input. Enforced by the grep gate requiring zero `${slug}` occurrences in the route file |
| T-9-15-01 | Information Disclosure | Unpublished or draft documents resolving via a guessed slug | mitigate | The by-slug queries from 09-07 constrain on published status; `notFound()` is returned for anything that does not resolve, so a guessed slug cannot reveal draft content |
| T-9-15-02 | Tampering | Editor content rendered into the page | accept | `category.overview` is a plain Sanity `text` field, not Portable Text, so React's default JSX escaping applies. This plan introduces no `dangerouslySetInnerHTML` and no Portable Text renderer — doing so later would be a new XSS surface and must be re-assessed |
| T-9-15-03 | Spoofing | Outbound WhatsApp link | mitigate | Built by `@/lib/whatsapp` from settings or the fallback constant, never from the URL or any visitor input |
| T-9-01 | Tampering | Search input | not applicable | No search surface in this plan |
| T-9-SC | Tampering | npm installs | not applicable | No new packages |

</threat_model>
